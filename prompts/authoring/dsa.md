# Authoring a DSA problem for swemock

This brief is self-contained. Give it to an AI assistant (or follow it yourself) to draft one problem
folder. Every draft still has to pass `pnpm content:validate <slug>`; that command is the judge of quality,
not the author's confidence.

## Rules that matter most

1. **Original wording.** Write the statement, title, examples, hints, and editorial yourself. Classic
   problem *ideas* are fine; never copy or paraphrase closely from LeetCode, HackerRank, a textbook, or
   anywhere else. Change the story, names, and example values.
2. **Correct, then tested.** The reference solutions are the source of truth for the tests. If both the
   Python and C++ references pass every test and the brute force (if any) agrees, the problem is
   consistent. Do not hand-write expected outputs for hidden tests.
3. **Fair constraints.** State constraints in the statement and make the largest test match them. The
   Python reference must finish a maximum-size test in well under the time limit (2 s default).

## Folder layout

```
content/dsa/<slug>/            slug: lowercase-words-with-hyphens
  problem.yaml                 metadata, signature, hints, follow-ups
  statement.md                 the problem, with Examples and Constraints sections
  editorial.md                 Intuition, Approach, Complexity, Pitfalls and edge cases
  checker.py                   only when the checker is custom
  solutions/
    reference.py               Python solution (class Solution / the design class)
    reference.cpp              C++ solution, same signature
    brute.py                   optional naive solution (required when tle_guard: true)
  tests/
    visible.json               3-5 sample tests, written by hand (shown to the user)
    gen.py                     generator for the hidden tests (fixed seed)
    hidden.json, meta.json     GENERATED by `pnpm content:gen`; commit them
```

Start with `pnpm content:new dsa <slug> --title "Title" --difficulty medium`, which creates all of this
with a tiny working example in every file.

## problem.yaml

```yaml
title: Short Original Title
difficulty: medium            # easy | medium | hard
tags: [sliding-window]        # 1-5 from DSA_TAGS in packages/content/src/dsa/manifest.ts
companies: []                 # leave empty unless you are sure
source: authored
reviewed: false               # a maintainer sets this after reading the problem
version: 1
signature:                    # written once; stubs and drivers for every language are generated
  kind: function
  name: longestWindow         # camelCase, becomes the method name
  params:
    - { name: s, type: string }
    - { name: k, type: int }
  returns: int
checker: { type: exact }      # see "Checkers"
limits: { time_ms: 2000, memory_mb: 256 }
tle_guard: false              # true => solutions/brute.py must time out on a stress test
hints:                        # exactly four, each revealing a little more; level 5 is editorial.md
  - "A nudging question."
  - "The key observation."
  - "The approach in words."
  - "Pseudocode."
followups:                    # 1-8 questions an interviewer asks after the solution
  - "What if the input is a stream?"
```

### Types

`int` (32-bit), `long`, `double`, `bool`, `char` (one-character string), `string`, `ListNode`, `TreeNode`,
plus `T[]` and `list<T>` (nest freely, e.g. `int[][]`, `list<list<int>>`; no arrays of lists).

- `ListNode` is written in tests as an array of values (`[1, 2, 3]`; `[]` is the empty list).
- `TreeNode` is level order with `null` for missing children (`[1, null, 2]`; `[]` is the empty tree).
- Test inputs are JSON objects keyed by parameter name: `{"nums": [1, 2], "k": 3}`.
- A `void` return is allowed only for design-class methods.

### Design-class problems

```yaml
signature:
  kind: design
  className: RecencyCache
  constructorParams: [{ name: capacity, type: int }]
  methods:
    - { name: get, params: [{ name: key, type: int }], returns: int }
    - { name: put, params: [{ name: key, type: int }, { name: value, type: int }], returns: void }
```

Test input is `{"ops": ["RecencyCache", "put", "get"], "args": [[2], [1, 10], [1]]}` and the expected
output is one entry per call, `null` for the constructor and for `void` methods:
`[null, null, 10]`. See `content/dsa/recency-cache`.

### Checkers

| Checker | Use when |
| --- | --- |
| `{ type: exact }` | exactly one correct output (compared type-strictly: `true` is not `1`) |
| `{ type: unordered }` | a list whose order does not matter (`nested: true` for lists of lists) |
| `{ type: float, tolerance: 1.0e-6 }` | floating-point answers |
| `{ type: custom, file: checker.py }` | many valid answers; see `content/dsa/course-order/checker.py` |

A custom checker defines `check(input, expected, actual)` and returns `True`/`False` or a tuple
`(ok, message)`. The message is shown for visible tests only. Prefer making the answer unique (a tie-break
rule in the statement) over a custom checker when that is natural.

## Reference solutions

Write them in the same style a good candidate would: the LeetCode-like `class Solution` with the method
from the signature (or the design class). Python gets `List`, `Optional`, `ListNode`, `TreeNode`,
`collections`, `heapq`, `bisect`, `math`, `itertools` without imports. C++ gets `bits/stdc++.h` and
`using namespace std`. `ListNode` and `TreeNode` are provided in both languages.

Avoid recursion deeper than a few thousand frames in the Python reference unless the problem needs it
(the sandbox allows deep recursion, but iterative code is a better model answer).

## tests/gen.py

Prints one JSON array to stdout: `[{"kind": "edge", "input": {...}}, ...]`. Inputs only; expected
outputs come from `solutions/reference.py`.

- **Fixed seed** (`rng = random.Random(12345)`). Validation reruns the generator and requires identical
  output.
- **At least 15 tests.** Kinds: `edge` (smallest, degenerate, boundary values: required), `random`, and
  `stress` (maximum size: required). Aim for 8-12 edge, 5-8 random, 3-5 stress.
- Every generated input must satisfy the constraints you state. Validation checks types, not your
  numeric bounds, so check the bounds yourself.
- Python standard library only. Keep the generated `hidden.json` under about 1.5 MB (use narrow value
  ranges for large arrays) so the repository stays light.
- When `tle_guard: true`, make the stress tests large enough that `brute.py` takes clearly more than the
  time limit, and keep every non-stress test small enough that it passes within the limit.

## statement.md and editorial.md

- Statement: a short description, `## Examples` (matching `tests/visible.json`), `## Constraints`.
  Math goes in `$...$` (KaTeX). Use fenced code blocks for example input and output.
- Editorial headings must include **Intuition**, **Approach**, **Complexity**, and **Pitfalls and edge
  cases** (validation checks for them). Explain *why* the approach works and what typically goes wrong.
- Never put the full solution in a hint before level 4 (pseudocode), and never put code in levels 1-3.

## Make it pass

```
pnpm content:gen <slug>        # runs gen.py, computes expected outputs, times both references
pnpm content:validate <slug>   # schema, tests vs signature, both references, brute force, reproducibility
```

Fix every message `content:validate` prints. It needs Docker and the sandbox images
(`docker compose build sandbox-python sandbox-cpp`). A passing problem shows up in the running app within
a few seconds; no rebuild needed.

## Self-check before you hand it in

- [ ] Title, statement, examples, hints, and editorial are my own wording.
- [ ] The slowest correct solution I would accept is within the time limit; a naive one is not (when `tle_guard`).
- [ ] The visible tests are meaningful samples, not just the smallest cases.
- [ ] Edge cases cover: empty or single input, duplicates, negatives and zero where allowed, the maximum
      values, and anything the constraints permit that a typical solution gets wrong.
- [ ] `reviewed: false` (a maintainer flips it after reading).
